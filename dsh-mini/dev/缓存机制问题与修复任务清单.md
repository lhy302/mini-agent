# dsh-mini 缓存机制问题排查报告与修复任务清单

> 本文档已完成实机对比测试与代码根因定案。
> 供接手修复的 Agent 快速阅读并按步骤直接实施修改与回归打包。

---

## 一、 背景与现象

用户反馈：在搭配本地 AI 服务器（`llama-server` / `ik_llama.cpp`，运行 `ornith-1.5-35b-a3b` 等思考模型）使用 `dsh-mini` 时，**多轮对话中模型首 Token（TTFT）越来越慢**。在长会话（20+ 轮）中，首 Token 甚至需要等待数十秒到数分钟。

经实测：服务端理论 Prefill 速度高达 130 tokens/秒，单次小请求仅需 0.3 秒；但在 `dsh-mini` 的长对话中，随着历史积累到 27,000 Tokens，每轮的首 Token 耗时高达 $27000 \div 130 \approx 200$ 秒。

---

## 二、 实测对比与根因结论

我们在本地真实运行的 `llama-server`（Ornith-35B）上进行了严格的 A/B 请求测试：

| 测试组 | 消息构造方式 | 首轮 Prefill | 次轮请求 Tokens | 次轮缓存命中（`cached_tokens`） | 缓存命中率 | 次轮响应速度 |
| :--- | :--- | :---: | :---: | :---: | :---: | :---: |
| **测试 A（正常缓存）** | 助手消息**完整回传 `reasoning_content`** | 26 tokens | 106 tokens | **89 tokens** | **84%**（命中） | **极速秒回** |
| **测试 B（dsh-mini 现状）** | 助手消息**丢弃 `reasoning_content`**，仅传 `content` | 26 tokens | 52 tokens | **0 tokens** | **0%（完全击穿）** | **全量重算，耗时翻倍** |

**核心根因定案**：
1. **思考模型前缀失配（P0 致命）**：`dsh-mini.py` 在 `Agent.run_turn` 保存历史消息时，**丢弃了助手的 `reasoning_content`**。服务端 Slot 内的 KV Cache 包含完整的 `<think>...</think>` tokens，但下一轮客户端回传时缺失了思考部分，导致 Jinja 渲染出来的文本在前缀处与 KV Cache 不一致，**服务端检测到 Token 失配后直接强制清空缓存并从头全量重算**！
2. **缓存监控盲区（P1 缺陷）**：`format_usage` 仅检查了 DeepSeek 专有字段 `prompt_cache_hit_tokens`，未兼容 OpenAI / llama.cpp 的 `prompt_tokens_details.cached_tokens`，导致界面和日志无法感知缓存状态。
3. **视觉 Base64 膨胀（P2 建议）**：自主看图或截屏后将几十万字符的 Base64 永久滞留在 `self.messages` 中，加剧上下文暴增。

## 三、 修复任务清单（待执行）

### 任务 1（P0 级）：在 `Agent.run_turn` 中保留 `reasoning_content`

* **目标文件**：`dsh-mini\dev\dsh-mini.py`
* **位置**：约 2957 行（`history_message` 构造处）
* **现状代码**：
  ```python
  history_message = {"role": "assistant", "content": assistant.get("content")}
  if assistant.get("tool_calls"):
      history_message["tool_calls"] = assistant["tool_calls"]
  if history_message["content"] is None and not history_message.get("tool_calls"):
      history_message["content"] = ""
  self.messages.append(history_message)
  ```
* **修改方案**：
  判断如果 `assistant` 字典中包含 `reasoning_content`（且不为空），将其原样保留在 `history_message` 中：
  ```python
  history_message = {"role": "assistant", "content": assistant.get("content")}
  if assistant.get("reasoning_content"):
      history_message["reasoning_content"] = assistant["reasoning_content"]
  if assistant.get("tool_calls"):
      history_message["tool_calls"] = assistant["tool_calls"]
  if history_message["content"] is None and not history_message.get("tool_calls"):
      history_message["content"] = ""
  self.messages.append(history_message)
  ```

### 任务 2（P1 级）：在 `format_usage` 中兼容 llama.cpp / OpenAI 缓存统计格式

* **目标文件**：`dsh-mini\dev\dsh-mini.py`
* **位置**：约 482 行（`format_usage` 函数）
* **现状代码**：
  ```python
  hit = usage.get("prompt_cache_hit_tokens")
  miss = usage.get("prompt_cache_miss_tokens")
  if hit is not None or miss is not None:
      parts.append("缓存命中=%s" % (0 if hit is None else hit))
      parts.append("未命中=%s" % (0 if miss is None else miss))
  ```
* **修改方案**：
  支持解析 `usage.get("prompt_tokens_details", {}).get("cached_tokens")`：
  ```python
  hit = usage.get("prompt_cache_hit_tokens")
  if hit is None and isinstance(usage.get("prompt_tokens_details"), dict):
      hit = usage["prompt_tokens_details"].get("cached_tokens")
  miss = usage.get("prompt_cache_miss_tokens")
  if hit is not None or miss is not None:
      parts.append("缓存命中=%s" % (0 if hit is None else hit))
      if miss is not None:
          parts.append("未命中=%s" % miss)
  ```

### 任务 3（P2 级，可选）：视觉 Base64 消息的历史修剪防膨胀

* **目标文件**：`dsh-mini\dev\dsh-mini.py`
* **位置**：约 3004 行
* **现状**：每次调用 `read_image` 或 `take_screenshot`，都会向 `self.messages` 注入数百 KB 的完整 Base64 图片并永久保留。
* **建议**：
  为避免多轮对话上下文因高频截屏/读图失控膨胀，可在跨轮多步执行时，仅保留最近 1~2 张图片的 Base64 数据 URL，更早历史轮次中的图片数据可精简替换为文本占位符 `[Image from <name> already inspected by model]`。
